## 着手前
1. 現在の repo、branch、commit、未コミット変更、制作中作業、既存スケジューラー、LOCK と引継ぎを読み取り確認する。
2. 同一対象の制作を重複起動しない。既存の担当が制作中なら、独立した読取りやレビュー準備を進める。
3. 作業台帳には task ID、対象、担当、目的、基準commit、更新時刻、次の担当、停止理由を記す。
4. LOCK の所有者や期限だけを理由に削除しない。古い状態は所有者または dot が確認する。
5. secrets、認証ファイル、キー、トークンは読取りやログの対象にしない。

## 待ち行列と切替
dot は、でこもんの独立レビュー・重大修正を優先し、その作業がない空き時間を虫のいる場所の制作へ割り当てる。既承認範囲と必要資源を確認し、同じ作業ツリー・ブラウザー・ポート等を二重起動しない。
切替は、変更と検証状況を保存し、引継ぎと使用資源を記録して解放できる安全な区切りで行う。承認待ち・環境制約は当該工程だけを停止し、独立して実施できる承認済み作業を進める。凍結・中止条件、公開方針、期限付き許可を暗黙に変更・延長しない。
待ち順の文書化だけで自動起動・監視が設定済み/稼働中と扱わない。現在はPR13の独立レビュー往復が最優先、虫制作/レビューは後続の記録のみで未起動。

## 最小の実働経路
既存の PR → Codexレビュー → Claude修正 → Codex再レビューを優先する。接続済み経路が足りるなら新APIキーや別スケジューラーを作らない。CLI/API/共有ファイルの経路は実際の受信確認を残してから「利用可能」とする。
dot は制作依頼、レビュー結果、修正commit、再テスト結果を同じ task ID で結ぶ。共有文書を書いただけでは相手に届いたことにならない。

## 独立レビューと完了条件
1. 制作担当は対象commit、変更理由、実行手順、既存テスト結果、既知制約を引き渡す。
2. 独立担当は差分と関連コードを読み、対象commitを記録する。旧commitの指摘が解消済みでも新headのレビュー済みとは扱わない。
3. 実ゲームの起動、画面確認、通常入力での進行をそれぞれ実施する。ソースを読んで「遊んだつもり」の検討は設計レビューであり実操作QAではない。
4. 自動モード、debug状態直行、ページ内 evaluate による状態変更は通常入力の通し確認と分ける。タイトル → 種類/開始 → 選択 → 戦闘 → 結果 → 次の選択または周回終了を実入力で通す。
5. 指摘は再現手順、期待、実測、重要度、証拠を添える。確認していない疑いは推測と書く。問題を作って修正実績を増やさない。
6. 制作担当が修正し、別担当が修正commitで同じ再現条件を再テストする。指摘者と制作担当の主張だけで解決済みにしない。
7. 全必須工程の証拠がそろうまで「開発完了」にしない。部分合格を全体合格に拡張しない。公開やmergeの判断は独立の承認工程。

## 工程ごとの状態
各工程を「未実施 / 合格 / 失敗 / 環境制約」で記録し、担当、対象commit、日時、手順、実測、証拠パスを必ず添える。
対象工程: Claude→Codex呼出し、コードレビュー、テスト実行、実ゲーム起動、画面確認、入力/進行、結果受渡し、修正、別担当の再テスト。
環境制約は失敗した試行とエラーを残す。dotクラウドのWebGL context制約を本人PCにも推定適用しない。本人PCのChrome等で試した結果を別記録にする。
スクリーンショット、動画、console/pageerror、テストstdout・stderr、終了コード、commitを同じ証拠フォルダに保存する。設定済み・予定・過去実績を今回の合格にしない。

## 機械判定
画面検査の終了コードは少なくとも例外/pageerror、要求周回未完、計算不一致、重なり/はみ出し、透け、点滅過多、規定サイズのスクロール違反を失敗にする。コンソールの行や表を出すだけでは合否ゲートにならない。
でこもんの既存 check.js の終了コードは内側スクロールを中心に判定している。現行の表と終了コード0だけを全体品質合格にしない。全指標を読み合わせ、通常入力の通し試験と独立レビューも必要。

## 修正の上限と停止
同一指摘の修正・再テストは原則3回まで。重大問題が残る、証拠不足、独立担当不在、権限不足、対象commit不明ならその工程を停止し理由を台帳へ記す。別の承認済み準備は続ける。
公開、merge、自動公開、課金、新規ログイン、永続アクセス、ネットワーク・権限拡大は、検証とは別に、対象へ適用される既承認範囲と安全条件を確認する工程として扱う。既に明示された承認の範囲内で安全条件を満たす操作に、毎回の本人再確認を必須化する意味ではない。過去の許可の適用が未確認なら今回の実行根拠にせず、現在の明示的な禁止を優先する。拒否を新たな証拠なしに繰り返さず迂回しない。本ケースのPRはdraft保存・更新だけが承認され、merge/deployは禁止のまま。

5. 小さな実対象を選び、受渡しから独立再検証まで1往復してから実働と報告する。
